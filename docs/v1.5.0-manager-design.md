# `v1.5.0` — `Manager` for MT cache + push hot-reload

**Status:** Design draft for implementation.
**Target release:** `v1.5.0` (minor — additive API + opt-in behaviour change in `Client.OnChange`).
**Driver:** D9 initiative in `plugin-br-bank-transfer` (see `docs/plans/D9-systemplane-mt-hot-reload-plan.md` and `docs/audits/D9-post-fred-audit.md` in that repo).

## Problem

`v1.4.0` ships database-per-tenant compliance, but disables the in-process cache and the LISTEN/NOTIFY changefeed in MT mode. The contract is documented in `internal/client/options.go`:

> *"The in-process cache and process-wide changefeed are disabled. Get hits the resolved tenant DB on every call. OnChange returns `ErrNotSupportedInMultiTenant`."*

The practical consequence for consumers running in MT:

- Every `Get` is a tenant-DB roundtrip (~ms vs ~ns in ST).
- No push hot-reload — an admin `Set` reaches running processes only on the next restart (no NOTIFY → no callback fire).
- Consumer-side caches that captured a `DefaultValue` at construction never refresh.

ST behaves correctly (cache seeded at `Start`, LISTEN goroutine refreshes it on NOTIFY). MT has equivalent intent but no implementation. The result is **temporary asymmetry** that `v1.5.0` closes.

## Goal

Bring MT to parity with ST internally — same correctness guarantees, same latency profile — without changing the consumer-facing API surface beyond a new `Manager` type and one behaviour-change in `Client.OnChange` (opt-in via Manager binding).

## Architecture target — symmetric with ST, scoped per tenant

```
ST today (kept as-is)             MT target (this design)
─────────────────────             ───────────────────────
Single Postgres DB                Each tenant has its own Postgres DB
└── trigger NOTIFY                └── trigger NOTIFY per tenant DB
    └── one LISTEN goroutine          └── one LISTEN goroutine per tenant
        └── in-process cache              └── in-process cache per tenant
                                              (map[tenantID]*tenantCache)
```

No new transports. No Redis on the data path. No coupling between `lib-systemplane` and other libraries beyond what already exists (`lib-commons/v5/commons/tenant-manager/{core,postgres}`).

## Public API

New file: `manager.go` at the package root (next to `api_client.go`).

```go
package systemplane

// Manager owns per-tenant LISTEN/NOTIFY bookkeeping and the per-tenant
// in-process cache in multi-tenant deployments. Constructed once per
// process, bound to a Client running in WithMultiTenantEnabled mode.
//
// Lifecycle handlers are wired by the consumer into its tenant lifecycle
// event plumbing (typically the lib-commons tenant-manager event dispatcher
// or the consumer's own wrapper around tenant-events:* subscription).
type Manager struct {
    client    *Client
    pgMgr     *tmpostgres.Manager
    perTenant sync.Map // tenantID string -> *tenantCache
    callbacks sync.Map // nskey -> []Callback (registered via Client.OnChange in MT)
    logger    log.Logger
    telemetry *tracing.Telemetry
    cfg       managerConfig
}

type ManagerOption func(*managerConfig)

func NewManager(client *Client, pgMgr *tmpostgres.Manager, opts ...ManagerOption) *Manager
func WithManagerLogger(logger log.Logger) ManagerOption
func WithManagerTelemetry(t *tracing.Telemetry) ManagerOption

// OnTenantActivated bootstraps systemplane state for tenantID:
//   1. Ensure the systemplane schema exists in the tenant DB (idempotent
//      CREATE TABLE IF NOT EXISTS, mirrors existing lazy-bootstrap in the
//      MT Postgres store but moved up-front).
//   2. Seed every registered key's DefaultValue with INSERT ... ON CONFLICT
//      (namespace, key) DO NOTHING. Never overwrites operator-set values.
//   3. Open a LISTEN goroutine on systemplane_events for the tenant DB.
//   4. Warm-load every registered key into the per-tenant cache.
//
// Idempotent. Safe to call multiple times. Returns the first non-nil error
// encountered (logs and continues for subsequent keys / steps).
func (m *Manager) OnTenantActivated(ctx context.Context, tenantID string) error

// OnTenantSuspended pauses the LISTEN goroutine for tenantID and marks the
// cache as stale. Cache entries are kept (suspension is reversible — fast
// reactivation avoids re-warming) but reads after suspension fall through
// to the tenant DB to recover fresh values.
func (m *Manager) OnTenantSuspended(ctx context.Context, tenantID string) error

// OnTenantDeleted closes the LISTEN goroutine for tenantID and evicts the
// cache. Frees process resources tied to the tenant.
func (m *Manager) OnTenantDeleted(ctx context.Context, tenantID string) error

// OnTenantCredentialsRotated closes the existing LISTEN goroutine, releases
// the existing per-tenant pool back to tmpostgres.Manager, then re-runs the
// OnTenantActivated sequence with refreshed credentials.
func (m *Manager) OnTenantCredentialsRotated(ctx context.Context, tenantID string) error
```

All four handlers MUST be:

- **Idempotent.** Calling twice in a row is safe; the second call observes existing state and no-ops the parts already done.
- **Order-tolerant.** Out-of-order delivery (e.g. `OnTenantSuspended` before `OnTenantActivated`) must not panic; the late `OnTenantActivated` rebuilds state correctly.
- **Non-blocking for unknown tenants.** Calling `OnTenantSuspended/Deleted/CredentialsRotated` for a tenant the Manager has never seen returns nil after logging at debug level (the tenant was never activated, nothing to tear down).

## `Client.OnChange` behavior change

Today (`v1.4.0`):

```go
func (c *Client) OnChange(ns, key string, cb Callback) (Unsubscribe, error) {
    if c.cfg.multiTenantEnabled {
        return nil, ErrNotSupportedInMultiTenant
    }
    // ... ST path: register on c.subscribers, drained by the LISTEN goroutine.
}
```

After (`v1.5.0`):

```go
func (c *Client) OnChange(ns, key string, cb Callback) (Unsubscribe, error) {
    if c.cfg.multiTenantEnabled {
        if c.manager == nil {
            // Caller opted into MT but did not bind a Manager.
            // Preserves v1.4.0 behaviour for callers not yet migrated.
            return nil, ErrNotSupportedInMultiTenant
        }
        return c.manager.registerCallback(ns, key, cb), nil
    }
    // ... ST path unchanged ...
}
```

`Manager.registerCallback` adds the callback to a per-`nskey` callback list (`m.callbacks` `sync.Map`). The per-tenant LISTEN goroutines consult this map on each NOTIFY arrival.

**No breaking change** for callers that don't bind a `Manager` — they continue to see `ErrNotSupportedInMultiTenant` exactly as today. The new behaviour is strictly opt-in.

### Binding the Manager to the Client

A new option on `Client`:

```go
// WithMultiTenantManager binds a Manager to the Client. When the Manager
// is non-nil, Client.OnChange in MT mode registers callbacks on the
// Manager's per-tenant LISTEN dispatcher instead of returning
// ErrNotSupportedInMultiTenant.
//
// The Manager must be constructed first via NewManager, then handed to the
// Client via this option. Tests can pass nil to keep v1.4.0 behaviour.
func WithMultiTenantManager(m *Manager) Option
```

Construction order in the consumer (the plugin):

```go
client, err := systemplane.NewPostgres(
    db, dsn,
    systemplane.WithMultiTenantEnabled(),
    systemplane.WithLogger(logger),
    systemplane.WithTelemetry(t),
)
// ...
manager := systemplane.NewManager(client, pgMgr,
    systemplane.WithManagerLogger(logger),
    systemplane.WithManagerTelemetry(t),
)
client.BindManager(manager) // or pass via constructor option; choice for the implementor
```

Two equivalent shapes are acceptable — `WithMultiTenantManager(m)` as a constructor option (requires building the manager first, awkward circular ref) **or** a post-construction `Client.BindManager(m)` method (cleaner since `Manager` needs the `Client` to be built first). Recommend the latter.

## Cache model

```go
type tenantCache struct {
    mu      sync.RWMutex
    entries map[nskey]any
    stale   bool // true after OnTenantSuspended; first Get triggers refresh
}

// Inside Manager:
perTenant sync.Map // tenantID string -> *tenantCache
```

- **No TTL.** The cache is authoritative as long as the LISTEN goroutine for that tenant is live. Same invariant as the ST cache.
- **Invalidation channels (in order of precedence):**
  1. **NOTIFY received** on the tenant's LISTEN connection → atomic update of the affected `entries` slot.
  2. **LISTEN connection drop detected** → evict the tenant's cache; lazy re-open on next `Get` (or next `OnTenantActivated`/`OnTenantCredentialsRotated` event). Defence in depth against missed NOTIFYs across reconnect windows.
  3. **Explicit handler:** `OnTenantDeleted` evicts; `OnTenantSuspended` marks stale.
- **Tenant-context resolution:** every `Client.Get*` extracts the tenant from `ctx` via `tmcore.GetPGContext(ctx, module)`. Same as today.

### Get path with Manager bound

```go
// Inside Client.GetInt (MT path):
func (c *Client) GetInt(ctx context.Context, ns, key string) (int, bool, error) {
    if c.manager != nil {
        return c.manager.getInt(ctx, ns, key) // cache lookup → DB miss fallback
    }
    // Fallback: v1.4.0 behaviour — DB roundtrip on every call.
    return c.getIntFromDB(ctx, ns, key)
}

// Inside Manager.getInt:
func (m *Manager) getInt(ctx context.Context, ns, key string) (int, bool, error) {
    tenantID, ok := tmcore.TenantIDFromContext(ctx) // or whatever tmcore exposes
    if !ok {
        return 0, false, nil // boot ctx without tenant — same semantics as today
    }

    tc := m.tenantCacheFor(tenantID) // load-or-create
    if !tc.stale {
        tc.mu.RLock()
        v, hit := tc.entries[nskey{ns, key}]
        tc.mu.RUnlock()
        if hit {
            return v.(int), true, nil
        }
    }

    // Miss or stale → resolve tenant DB via pgMgr, read, populate cache.
    return m.loadFromTenantDB(ctx, tenantID, ns, key)
}
```

The Manager populating the cache on cache miss serves the same role the lib's lazy hydration does for ST. After the first Get for a (tenant, key), subsequent reads are O(1) until invalidation.

## Per-tenant LISTEN goroutine

Each active tenant has one goroutine:

```
loop:
    conn = pgMgr.GetConn(ctx_for_tenant)  // dedicated LISTEN connection
    LISTEN systemplane_events
    for {
        notification = conn.WaitForNotification()
        if notification.payload contains tenant mismatch (impossible normally,
            defence in depth) → log boundary error, ignore
        decode {namespace, key, op}
        if op == "delete":
            tc.delete(nskey)
        else if op == "upsert":
            value = read fresh from tenant DB
            tc.set(nskey, value)
            for each cb in m.callbacks[nskey]:
                go cb(ctx, ns, key, value)  // via lib-observability/runtime.SafeGo
    }
on conn drop:
    evict tc, log, return; goroutine exits.
    Lazy re-open on next OnTenantActivated or OnTenant... or next Get
        (a "reopen-LISTEN-if-down" hook on Get path is the simplest).
```

Implementation notes:

- Use `lib-observability/runtime.SafeGo` for the goroutine so panics are observable.
- Use `pgx` notification semantics already in use by the existing ST `postgres_listen.go` — mirror that file's loop, just per-tenant.
- Pool reuse: the LISTEN connection is acquired via `pgMgr.GetConn` so it sits inside the tenant's pool budget; the operator already provisioned for this. Document the impact (one extra long-lived connection per active tenant).

## Schema bootstrap and default seeding

`OnTenantActivated` performs:

1. **`CREATE TABLE IF NOT EXISTS systemplane_entries (...)`** + the NOTIFY trigger if absent. Mirrors the lazy-bootstrap that today happens on first `Get` in MT mode — Manager makes it eager so the first request does not pay the cold-start cost.
2. **Seed defaults.** For each registered key, `INSERT INTO systemplane_entries (namespace, key, value) VALUES (...) ON CONFLICT (namespace, key) DO NOTHING`. Idempotent — never overwrites operator-set values.
3. **Warm-load.** `SELECT namespace, key, value FROM systemplane_entries` populates `tenantCache.entries`.

The seed step is what removes the need for plugins to ship hand-rolled `INSERT ON CONFLICT` migrations (the `plugin-br-bank-transfer/migrations/000011_systemplane_defaults_seed.up.sql` stop-gap goes away). The lib owns the schema and the defaults; the migration disappears in the plugin's Phase 6 follow-up.

## Tenant-context invariants

The Manager only operates inside ctx that has a tenant resolved by `tmcore`. Specifically:

- `Manager.OnTenant*(ctx, tenantID)` handlers are expected to be called from the consumer's tenant lifecycle event plumbing **after** a tenant ctx has been built. The handler's first step is `ctx_tenant := tmcore.WithTenantID(ctx, tenantID)` (or equivalent — match what tmcore exposes).
- `Manager.getInt(ctx, ...)` extracts the tenant from ctx via `tmcore`. No tenant → returns `(zero, false, nil)`. Same semantics as today.
- The per-tenant LISTEN goroutine carries an internal ctx tied to that one tenant; cache writes never cross tenant boundaries.

Defence in depth: each LISTEN notification payload includes the tenantID (or the receiving goroutine knows which tenant it's bound to); if a stray notification arrives with a different tenantID (impossible normally — different tenants are in different DBs), the goroutine logs and ignores. Tests with concurrent multi-tenant traffic assert no cross-contamination of cache entries.

## Telemetry

New metrics (opt-in via `WithManagerTelemetry`):

| Metric | Type | Labels | Description |
|---|---|---|---|
| `systemplane.manager.tenants_active` | gauge | — | Number of tenants with a live LISTEN goroutine. |
| `systemplane.manager.cache_entries` | gauge | `tenant_id` | Entries currently cached per tenant. |
| `systemplane.manager.notify_received_total` | counter | `tenant_id`, `op` | NOTIFYs received per tenant. |
| `systemplane.manager.listen_disconnects_total` | counter | `tenant_id`, `reason` | LISTEN connection drops. |
| `systemplane.manager.warmload_latency` | histogram | `tenant_id` | OnTenantActivated end-to-end latency. |
| `systemplane.manager.get_cache_hits_total` | counter | `tenant_id`, `outcome` (hit/miss) | Per-tenant cache hit rate. |

Labels with `tenant_id` should respect tenant cardinality limits — emit a special `tenant_id="aggregate"` rollup when active-tenant count exceeds a configurable threshold (defaults: ~1000). Implementation detail; document in the Manager's logger doc-comment.

## Versioning and compatibility

**Target:** `v1.5.0` — minor bump, additive API.

| Surface | v1.4.0 | v1.5.0 |
|---|---|---|
| `Client` constructor signature | unchanged | unchanged |
| `Client.Get*` API | unchanged | unchanged externally; in MT with Manager bound, hits cache |
| `Client.OnChange` in MT without Manager | returns `ErrNotSupportedInMultiTenant` | **unchanged** (preserves v1.4.0 behaviour) |
| `Client.OnChange` in MT with Manager bound | N/A | registers on Manager — new behaviour, opt-in |
| New types | — | `Manager`, `ManagerOption`, related option helpers |

**Strict backward compatibility.** Callers not migrating to bind a Manager observe identical behaviour to v1.4.0. The lib continues to ship the existing ST cache + LISTEN/NOTIFY unchanged. The new code path is entirely opt-in via Manager binding.

## Implementation plan

Suggested commit / PR sequence (each commit lands a coherent slice):

1. **`feat(manager): scaffolding`** — empty `manager.go`, type declarations, `NewManager` returning a non-functional struct. No behavior change to existing surface. Add `Client.BindManager` no-op stub.
2. **`feat(manager): per-tenant cache`** — `tenantCache` + `sync.Map`-backed `perTenant`. Implement `Manager.getInt/getBool/getInt64/getString` against an empty cache (always misses → DB read). Route `Client.Get*` in MT through Manager when bound.
3. **`feat(manager): tenant lifecycle handlers (schema + seed)`** — `OnTenantActivated` implements schema bootstrap + defaults seed via `INSERT ON CONFLICT DO NOTHING`. `OnTenantDeleted` evicts. `OnTenantSuspended`/`CredentialsRotated` skeletons. No LISTEN yet.
4. **`feat(manager): per-tenant LISTEN goroutine`** — open LISTEN in `OnTenantActivated`; close in `OnTenantDeleted`/`OnTenantSuspended`. Cache updates on NOTIFY reception. Reopen-on-credentials-rotation.
5. **`feat(manager): OnChange MT-aware`** — `Manager.registerCallback`; `Client.OnChange` MT path routes through Manager when bound, returns existing error otherwise.
6. **`feat(manager): telemetry`** — emit the metrics listed above.
7. **`test(manager): unit`** — fake `tmpostgres.Manager`, idempotency tests for each handler, out-of-order delivery tolerance, unknown-tenant no-op behaviour.
8. **`test(manager): integration`** — `testcontainers-go` Postgres; NOTIFY end-to-end for a single tenant; concurrent traffic across multiple tenants (no cross-contamination); reconnect after `pg_terminate_backend`; `OnTenantDeleted` + `OnTenantActivated` round-trip for the same tenant (no leaks).
9. **`test(manager): goroutine leak`** — `goleak.VerifyNone` for each lifecycle path.
10. **`docs(manager): public API documentation`** — godoc on every exported symbol; example usage in `examples/manager/main.go`.
11. **`chore(release): v1.5.0`** — CHANGELOG entry; version bump.

Estimated effort: ~3-5 commits per slice on a typical workday; total perhaps 2-3 dev-days assuming familiarity with the existing internal/postgres LISTEN implementation.

## Postgres connection budget

Each active tenant adds one LISTEN connection per plugin replica. For a service with N active tenants and M replicas, the cluster sees N × M LISTEN connections in addition to the regular query connections.

Postgres comfortably handles thousands of LISTEN connections per node, but operators with large fleets should:

- Size `max_connections` accordingly. Conservative starting point: `max_connections >= 4 × (N × M)` plus headroom for the existing query pool.
- Confirm the per-tenant pool budget in `tmpostgres.Manager` includes the LISTEN slot.
- Monitor `systemplane.manager.tenants_active` × `systemplane.manager.listen_disconnects_total` rate as the canonical "did push hot-reload silently degrade" signal.

Connection-pool dispatching reuses `tmpostgres.Manager`'s existing per-tenant pool, so the LISTEN connection sits inside the budget the operator already provisioned for the tenant.

## Consumer integration (plugin side)

The plugin (`plugin-br-bank-transfer`) integrates the Manager in its `wrapTenantLifecycleHandler` (`internal/bootstrap/multi_tenant.go`) — the same handler that today routes events to `tenantIntegrationResolver` and the TED IN poller:

```go
// Inside wrapTenantLifecycleHandler, after the existing dispatcher.HandleEvent call:
if s.spManager != nil {
    var spErr error
    switch event.EventType {
    case tmevent.EventTenantActivated:
        spErr = s.spManager.OnTenantActivated(ctx, event.TenantID)
    case tmevent.EventTenantSuspended:
        spErr = s.spManager.OnTenantSuspended(ctx, event.TenantID)
    case tmevent.EventTenantDeleted:
        spErr = s.spManager.OnTenantDeleted(ctx, event.TenantID)
    case tmevent.EventTenantCredentialsRotated:
        spErr = s.spManager.OnTenantCredentialsRotated(ctx, event.TenantID)
    }
    if spErr != nil {
        s.log(ctx, liblog.LevelWarn, "systemplane manager lifecycle handling failed", ...)
    }
}
```

No change to `lib-commons/tenant-manager/event/dispatcher.go` — the plugin already owns the handler wrapping and can add this branch without any cross-lib coordination. The `WithSystemplane` `DispatcherOption` originally proposed in the plugin's D9 plan was cancelled for this reason.

## Open questions for the implementor

- Should `Manager` expose a `Drain()` method that closes all LISTEN goroutines on shutdown (for graceful drain), or is GC + ctx cancellation sufficient? Recommend: yes, explicit `Drain(ctx)` called from the consumer's shutdown sequence.
- What is the right behaviour when a tenant LISTEN goroutine repeatedly fails to reconnect? Bounded retry → mark stale → log boundary error? Backoff parameters? Recommend: exponential backoff capped at 30s, mark cache stale after 3 consecutive failures, never give up entirely.
- Should the LISTEN goroutine block startup of the Manager, or always be lazy on first event? Recommend: lazy (move the LISTEN open into `OnTenantActivated`, not into `NewManager`).
- Cache size limits per tenant — relevant only if a single tenant has very many keys. With ~50 registered keys total, the per-tenant cache is tiny. Document as a non-issue at current scale but worth pinning a bound (`MaxEntriesPerTenant = 10_000`?) defensively.

## Notes for review

This design preserves the v1.4.0 contract strictly for callers not opting into the Manager. No existing consumer's behaviour changes unless it actively binds a Manager via `Client.BindManager`. The implementation can land incrementally per the slice plan above; intermediate states keep ST and MT (without Manager) fully functional.
